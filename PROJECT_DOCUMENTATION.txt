1. PROJECT DESCRIPTION & OBJECTIVES
================================================================================

PROJECT ABSTRACT:
The Airline Management System is a comprehensive database application designed to 
streamline airline operations including flight scheduling, passenger management, 
ticket booking, and staff coordination. The system provides efficient data 
management for airlines to handle day-to-day operations.

PURPOSE:
- Automate airline booking and management processes
- Maintain centralized database for flights, passengers, and bookings
- Enable efficient query and reporting capabilities
- Provide secure admin and staff access control

MODULES INVOLVED:
1. Aircraft Management - Manage aircraft fleet details
2. Airport Management - Store airport information
3. Flight Management - Schedule and track flights
4. Passenger Management - Register and manage passenger data
5. Booking Management - Handle ticket reservations
6. Ticket Management - Generate and track tickets
7. Staff Management - Manage airline staff assignments
8. Admin Management - System administration and control

KEY FEATURES:
- Real-time flight availability checking
- Automated seat management
- Passenger booking history
- Staff assignment to flights
- Multi-airport operations support
- Ticket generation and cancellation
- Flight status tracking
- Revenue and booking analytics

GOALS:
- Reduce manual booking errors
- Improve operational efficiency
- Provide quick access to flight information
- Enable data-driven decision making
- Ensure data integrity and consistency
- Support scalable airline operations

RELATIONSHIPS:

1. AIRCRAFT to FLIGHTS (1:N)
   - One aircraft can be assigned to multiple flights
   - Cardinality: 1 Aircraft -> Many Flights

2. AIRPORTS to FLIGHTS (1:N) - Departure
   - One airport can have multiple departing flights
   - Cardinality: 1 Airport -> Many Flights

3. AIRPORTS to FLIGHTS (1:N) - Arrival
   - One airport can have multiple arriving flights
   - Cardinality: 1 Airport -> Many Flights

4. PASSENGERS to BOOKINGS (1:N)
   - One passenger can make multiple bookings
   - Cardinality: 1 Passenger -> Many Bookings

5. FLIGHTS to BOOKINGS (1:N)
   - One flight can have multiple bookings
   - Cardinality: 1 Flight -> Many Bookings

6. BOOKINGS to TICKETS (1:1)
   - Each booking generates one ticket
   - Cardinality: 1 Booking -> 1 Ticket

7. STAFF to FLIGHTS (M:N) - Can be extended with assignment table
   - Multiple staff members can be assigned to multiple flights

3. DATABASE SCHEMA DETAILS
================================================================================

All database schema is available in: database_schema.sql

KEY CONSTRAINTS IMPLEMENTED:

1. PRIMARY KEYS:
   - Auto-incrementing IDs for all tables
   - Ensures unique identification of records

2. FOREIGN KEYS:
   - flights.aircraft_id → aircraft.aircraft_id
   - flights.departure_airport_id → airports.airport_id
   - flights.arrival_airport_id → airports.airport_id
   - bookings.passenger_id → passengers.passenger_id
   - bookings.flight_id → flights.flight_id
   - tickets.booking_id → bookings.booking_id
   - staff_assignments.staff_id → staff.staff_id
   - staff_assignments.flight_id → flights.flight_id

3. UNIQUE CONSTRAINTS:
   - airports.airport_code
   - passengers.email
   - passengers.passport_number
   - flights.flight_number
   - tickets.ticket_number
   - staff.email
   - admins.username
   - admins.email
   - bookings: (flight_id, seat_number) combination

4. CHECK CONSTRAINTS:
   - aircraft.total_seats > 0
   - flights.available_seats >= 0
   - flights.price > 0
   - flights.departure_airport_id != arrival_airport_id
   - flights.arrival_time > departure_time
   - tickets.price > 0

5. ENUM CONSTRAINTS:
   - aircraft.status: 'Active', 'Maintenance', 'Retired'
   - flights.status: 'Scheduled', 'Boarding', 'Departed', 'Arrived', 'Cancelled', 'Delayed'
   - bookings.booking_status: 'Confirmed', 'Cancelled', 'Pending'
   - staff.role: 'Pilot', 'Co-Pilot', 'Flight Attendant', 'Ground Staff', 'Engineer'

6. DEFAULT VALUES:
   - Timestamps: CURRENT_TIMESTAMP
   - Status fields: Default to active/scheduled states

7. CASCADE RULES:
   - ON DELETE CASCADE: bookings, tickets, staff_assignments
   - ON DELETE RESTRICT: flights (cannot delete aircraft/airports with active flights)

9. VIVA PREPARATION POINTS
================================================================================

KEY CONCEPTS TO EXPLAIN:

1. NORMALIZATION:
   - Database is in 3NF (Third Normal Form)
   - No transitive dependencies
   - Minimal data redundancy

2. ACID PROPERTIES:
   - Atomicity: Booking transaction is all-or-nothing
   - Consistency: Constraints maintain data integrity
   - Isolation: Concurrent bookings handled properly
   - Durability: Committed transactions are permanent

3. INDEXING:
   - Primary keys automatically indexed
   - Foreign keys should be indexed for JOIN performance
   - Consider indexing on frequently searched columns (email, flight_number)

4. TRANSACTIONS:
   - Booking process uses implicit transactions
   - Stored procedures ensure atomic operations
   - Rollback on errors

5. TRIGGERS VS STORED PROCEDURES:
   - Triggers: Automatic, event-driven (after INSERT/UPDATE)
   - Procedures: Manual invocation, can have parameters
   - Both used for business logic enforcement

6. JOINS:
   - INNER JOIN: Only matching records
   - LEFT JOIN: All from left table + matching from right
   - Used extensively for combining flight, passenger, booking data

7. SUBQUERIES:
   - Nested SELECT statements
   - Used for complex filtering and aggregation
   - Can be correlated or non-correlated

8. VIEWS:
   - Virtual tables
   - Simplify complex queries
   - Provide data abstraction layer

EXPECTED VIVA QUESTIONS:

Q1: Why did you use triggers for seat management?
A: Triggers ensure automatic seat count updates whenever a booking is made or cancelled, maintaining data consistency without manual intervention.

Q2: Explain the relationship between bookings and tickets.
A: One-to-one relationship. Each booking generates exactly one ticket, enforced by UNIQUE constraint on booking_id in tickets table.

Q3: How do you prevent double booking of the same seat?
A: UNIQUE constraint on (flight_id, seat_number) combination in bookings table prevents duplicate seat assignments.

Q4: What happens if you try to delete an aircraft that has scheduled flights?
A: The DELETE operation fails due to FOREIGN KEY constraint with RESTRICT action, preventing orphaned flight records.

Q5: How would you implement a refund system?
A: Add a refunds table with booking_id FK, refund_amount, refund_date, and status. Update booking_status to 'Refunded'.

Q6: Explain the use of CHECK constraints in your schema.
A: CHECK constraints enforce business rules at database level (e.g., price > 0, seats >= 0, arrival_time > departure_time).

Q7: Why use stored procedures instead of handling everything in PHP?
A: Stored procedures provide better performance, reusability, security, and centralized business logic that can be called from multiple applications.

Q8: How do you handle concurrent bookings for the last available seat?
A: Database-level locking and transaction isolation ensure only one booking succeeds. The stored procedure checks availability within the transaction.
